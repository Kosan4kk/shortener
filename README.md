# Сервис сокращения URL

Небольшой HTTP-сервис на Go. Принимает длинную ссылку, возвращает короткую
и перенаправляет по ней на исходный адрес. Пользователь определяется по подписанной
cookie и может получить список своих ссылок.

Данные хранятся в памяти процесса. Базы данных и сторонних библиотек нет.

## Запуск

Понадобится [Go](https://go.dev/dl/) версии 1.22 или новее.
Все команды выполняются из папки проекта, где лежит `go.mod`.

```sh
go run ./cmd/shortener
```

Сервер доступен по адресу `http://localhost:8080`. Остановка: Ctrl+C.
При остановке сервер ждёт завершения текущих запросов до 5 секунд.

В другом терминале можно запустить тесты:

```sh
go test ./...
```

## Примеры запросов

Создадим ссылку. Cookie сохранится в файл `cookies.txt`:

```sh
curl -i -c cookies.txt \
  -H 'Content-Type: application/json' \
  -d '{"url":"https://example.com/some/long/path"}' \
  http://localhost:8080/api/shorten
```

Ответ `201 Created`, cookie `user_id` и JSON:

```json
{"result":"http://localhost:8080/1"}
```

Здесь `1` указан для примера. Используйте ссылку из своего ответа.
Проверим переход:

```sh
curl -i http://localhost:8080/1
```

Ответ будет `307 Temporary Redirect`. Исходный адрес находится в заголовке
`Location`. Cookie для перехода не нужна.

Теперь запросим список с сохранённой cookie:

```sh
curl -i -b cookies.txt http://localhost:8080/api/user/urls
```

Ответ `200 OK`:

```json
[
  {
    "short_url":"http://localhost:8080/1",
    "original_url":"https://example.com/some/long/path"
  }
]
```

При следующих сокращениях передавайте ту же cookie через `-b cookies.txt`.
Без неё сервер создаст нового пользователя с отдельным списком.

## API и ошибки

| Запрос | Ответ |
| --- | --- |
| `POST /api/shorten` | `201` и объект с полем `result` |
| `GET /{id}` | `307` с исходным URL в `Location`, либо `404`, если ID не найден |
| `GET /api/user/urls` | `200` и массив ссылок, либо `204` без тела, если список пуст |

В `POST /api/shorten` нужен один JSON-объект с полем `url` строкового типа.
Принимаются абсолютные HTTP/HTTPS адреса с непустым хостом. Пробелы и управляющие
символы нужно кодировать, порт должен быть от 1 до 65535.
Сервис сохраняет адрес как есть и не проверяет доступность исходного сайта.

Некорректный JSON или URL возвращает `400`. Лишние поля и несколько объектов
в одном запросе тоже отклоняются. Ограничение тела запроса составляет 1 МиБ,
при превышении сервер возвращает `413`.

Если указан Content-Type, требуется `application/json`.
Параметр `charset=utf-8` допускается. Другой тип возвращает `415`.
Неподдерживаемый метод возвращает `405` с заголовком `Allow`, внутренняя ошибка
возвращает `500`. Ошибки приходят в JSON: `{"error":"описание"}`.

## Cookie

Cookie называется `user_id`, значение имеет вид `userID:signature`.
ID создаётся из 16 случайных байт через `crypto/rand`.
Подпись вычисляется с помощью HMAC-SHA256, обе части записываются в hex.
Для сравнения подписей используется `hmac.Equal`.

| Cookie | Создание ссылки | Получение списка |
| --- | --- | --- |
| Отсутствует | Новая cookie и новый пользователь | Новая cookie и `204` |
| Валидная | Ссылка добавляется текущему пользователю | Только его ссылки, `200` или `204` |
| Пустая или с неправильным форматом | Новая cookie | `401` |
| ID есть, но подпись неверна | Новая cookie и новый пользователь | Новая cookie и `204` |

Неправильный формат: нет ID, разделителя или подписи, либо есть лишние части.
Изменение ID или подписи не даёт доступа к чужому списку.
Cookie имеет `Path=/`, `HttpOnly`, `SameSite=Lax` и срок 30 дней.
При HTTPS в `BASE_URL` добавляется `Secure`. Ответы имеют `Cache-Control: no-store`.

```sh
# Новый пользователь, 204.
curl -i http://localhost:8080/api/user/urls

# Пустая cookie, 401.
curl -i -H 'Cookie: user_id=' http://localhost:8080/api/user/urls

# Неправильный формат, 401.
curl -i -H 'Cookie: user_id=broken' http://localhost:8080/api/user/urls

# Неверная подпись, новая cookie и 204.
curl -i -H 'Cookie: user_id=someone:deadbeef' http://localhost:8080/api/user/urls
```

## Настройки

Все настройки необязательны. Файл `.env` автоматически не загружается.

| Переменная | По умолчанию | Для чего |
| --- | --- | --- |
| `SERVER_ADDRESS` | `:8080` | Адрес прослушивания |
| `BASE_URL` | `http://localhost:8080` | Публичный адрес в коротких ссылках |
| `SECRET_KEY` | `super-secret-key` | Ключ подписи cookie |

Запуск на другом порту:

```sh
SERVER_ADDRESS=127.0.0.1:9090 \
BASE_URL=http://localhost:9090 \
SECRET_KEY='replace-with-your-own-random-secret' \
go run ./cmd/shortener
```

Если меняете порт, укажите его в обеих настройках.
`BASE_URL` должен содержать HTTP/HTTPS адрес без пути, логина, пароля, query или fragment.
Завершающий `/` допускается. Заголовок Host клиента для построения ссылок не используется.
Сам сервер работает по HTTP. Для HTTPS нужен внешний reverse proxy.

Учебный ключ в коде разрешён заданием. Для своего сервера задайте случайный
`SECRET_KEY` через окружение. После смены ключа старые cookie станут недействительными.

## Устройство проекта

```text
cmd/shortener/main.go            запуск и остановка сервера
internal/app/app.go              обработчики, валидация и JSON
internal/app/app_test.go         тесты HTTP API
internal/auth/cookie.go          выдача и проверка cookie
internal/auth/cookie_test.go     тесты подписи и парсера
internal/storage/memory.go       хранение ссылок
internal/storage/memory_test.go  тесты хранилища
go.mod
Makefile
```

В хранилище две map: URL по коротким ID и ссылки по пользователям.
Доступ защищён `sync.RWMutex`. ID создаётся и записывается в оба индекса под одной
блокировкой. Список возвращается как копия в порядке создания ссылок.

Короткий ID получается из счётчика `uint64` в base-36: `1`, ..., `9`, `a`, ..., `z`, `10`.
В пределах процесса ID не повторяются. Переполнение счётчика возвращает ошибку.
Повторное сокращение одного URL создаёт отдельную ссылку.

После перезапуска все данные теряются, счётчик начинается заново.
Короткие ссылки публичны и предсказуемы. Cookie ограничивает доступ к списку
пользователя, но не к переходу. Постоянного хранения и ограничения количества
записей в этом учебном проекте нет.

## Проверки и сборка

```sh
go test ./...
go vet ./...
go test -race -cover ./...
gofmt -l cmd internal
```

При правильном форматировании последняя команда ничего не выводит.
Для `-race` нужен C toolchain и поддерживаемая платформа.
Обычные тесты запускаются без него. Если есть `make`, все проверки можно
выполнить командой `make check`.

В `.github/workflows/ci.yml` настроены такие же проверки и сборка для GitHub Actions.
Они запускаются при push и создании pull request.

Тесты проверяют все сценарии задания, неверные запросы, настройки и параллельную
работу. Есть проверки переполнения счётчика и ошибки генератора случайных чисел.
Отдельный тест работает с локальным HTTP-сервером через клиент с `cookiejar`.

Дополнительная проверка парсера cookie:

```sh
go test ./internal/auth -run='^$' -fuzz=FuzzParse -fuzztime=10s
```

Сборка исполняемого файла:

```sh
go build -o bin/shortener ./cmd/shortener
./bin/shortener
```

## Отправка на проверку

Загрузите содержимое этой папки в корень репозитория. Рядом с README должны
лежать `go.mod`, `cmd` и `internal`, чтобы команды из задания работали сразу.
Файл `go.sum` не нужен, потому что внешних зависимостей нет.

Перед отправкой выполните `go test ./...` и проверьте примеры запросов.
Cookie, секреты, бинарники и отчёты покрытия в репозиторий не нужны.
После загрузки отправьте ревьюеру ссылку на репозиторий.
